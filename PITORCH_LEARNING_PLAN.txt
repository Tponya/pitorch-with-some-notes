program behaves. Add concise guidance inside selected source files and keep
longer explanations in docs/learning/.

ANNOTATION LABELS
-----------------
C NOTE:        C language syntax or programming concept.
HARDWARE NOTE: Raspberry Pi, memory, GPIO, UART, GPU, or bare-metal behavior.
LLM NOTE:      Tokenization, transformer, sampling, inference, or training.
FLOW:          Where execution or data came from and where it goes next.
CAUTION:       A subtle point or likely misunderstanding.


WHAT EACH ANNOTATED FILE SHOULD CONTAIN
---------------------------------------
1. A short file-level reading guide:
   - why the file exists
   - who calls it
   - what it calls
   - important inputs and outputs
   - what file to read next

2. Section comments before major stages.

3. Function comments covering:
   - purpose
   - important parameters
   - return value or side effects
   - its place in the larger execution flow

4. Line-level notes only for genuinely difficult syntax or concepts.


REPEAT THIS CYCLE FOR EACH FILE GROUP
-------------------------------------
1. ORIENT
   Skim comments, includes, constants, structures, and function names.

2. MAP
   Determine why the file exists, who calls it, and what it calls.

3. TRACE
   Follow one execution path without immediately opening every called function.

4. ANNOTATE
   Add file, section, function, and selected line-level explanations.

5. REVIEW
   Inspect the diff and confirm that no executable behavior changed.

6. STUDY
   Read the annotated file and ask focused questions about confusing sections.

7. TEACH BACK
   Explain the file in a few sentences, then ask Codex to correct the summary.

8. COMMIT
   After approval, make one focused commit for that file group.
